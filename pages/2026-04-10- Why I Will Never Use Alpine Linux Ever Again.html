Why I Will Never Use Alpine Linux Ever Again
为什么我再也不会用 Alpine Linux

Martin
Mar 6, 2023
KubernetesDevOpsDocker

Nowadays, Alpine Linux is one of the most popular options for container base images. Many people (maybe including you) use it for anything and everything. Some people use it because of its small size, some because of habit and some, just because they copy-pasted a Dockefile from some tutorial. Yet, there are plenty of reasons why you should not use Alpine for your container images, some of which can cause you great amount of grief...
如今，Alpine Linux 已成为容器基镜像中最受欢迎的选择之一。很多人（可能包括你）会用它做各种事情。有些人用它因为它体积小，有些人是习惯性，还有些人只是因为他们从某个教程里复制粘贴了一个 Dockefile。然而，有很多理由不应该用 Alpine 拍摄容器照片，其中一些原因会给你带来很大麻烦......

The Source of All The Grief
所有悲痛的根源

To understand what makes Alpine a bad choice in some situations, we first need to talk about musl. musl is an implementation of C standard library. It is more lightweight, faster and simpler than glibc used by other Linux distros, such as Ubuntu. Both of these implementations are interchangeable for the most part, that's why in most cases you can switch from e.g., Ubuntu to Alpine and never notice any difference.
要理解为什么阿尔卑斯在某些情况下是个糟糕的选择，我们首先需要谈谈 musl。musl 是 C 标准库的实现。它比其他 Linux 发行版（如 Ubuntu）使用的 glibc 更轻量、更快、更简单。这两种实现在大多数情况下是可以互换的，这也是为什么大多数情况下你可以从比如 Ubuntu 切换到 Alpine，几乎感觉不到差别。

However, the little differences can cause all the grief. Some of it stems from how musl (and therefore also Alpine) handles DNS (it's always DNS), more specifically, musl (by design) doesn't support DNS-over-TCP. Usually, you would not notice this difference, because most of the time a single UDP packet (512 bytes) is enough to resolve hostnames... until it isn't enough and your application (running on Kubernetes) that previously worked completely fine for months suddenly starts throwing "Unknown Host" exceptions for one particular (very critical) hostname. The worst part is that this can manifest randomly, anytime when some external network change causes the resolution of some particular domain to require more than the 512 bytes available in single UDP packet.
然而，这些细微的差异往往会带来所有的痛苦。部分原因在于 musl（因此也是 Alpine）处理 DNS 的方式（总是 DNS），更具体地说，musl（设计上）不支持 DNS-over-TCP。通常你不会注意到这个差别，因为大多数情况下，单个 UDP 包（512 字节）就足以解析主机名......直到不够，你的应用程序（运行在 Kubernetes 上）之前几个月运行良好，突然开始针对某个（非常关键的）主机名抛出 “未知主机” 异常。最糟糕的是，这种情况可能随机出现，任何时候当外部网络变化导致某个特定域的解析需要超过单个 UDP 包中可用的 512 字节时。


By using Alpine, you're getting "free" chaos engineering for you cluster.
使用 Alpine，你为集群获得了“免费”的混沌工程。

For more details about this particular problem check out this great write-up: Does Alpine resolve DNS properly?
想了解更多关于这个问题的细节，可以看看这篇很棒的文章：Alpine 能正确解析 DNS？

If you run tens or even hundreds of microservices/applications all based on Alpine, and they all suddenly stop working and the only fix is to switch to different Linux distro, which requires rebuilding all the applications and redeploying them, then you can be faced with extremely disruptive, multi-day outage.
如果你运行了数十甚至数百个基于 Alpine 的微服务/应用，它们突然全部停止工作，唯一的解决办法是切换到不同的 Linux 发行版，这需要重建所有应用并重新部署，那么你可能会面临极其干扰的多天宕机。

Finally, this DNS issue does not manifest in Docker container. It can only happen in Kubernetes, so if you test locally, everything will work fine, and you will only find out about unfixable issue when you deploy the application to a cluster. Also, Kubernetes docs claim that DNS issues are relevant only for "Alpine version 3.3 or earlier", but I encountered the above issue on Alpine 3.16, so go figure.
最后，这个 DNS 问题在 Docker 容器中并未表现出来。这只能在 Kubernetes 中发生，所以如果你在本地测试，一切都会正常，只有在将应用部署到集群时才会发现无法修复的问题。另外，Kubernetes 文档声称 DNS 问题只适用于 “Alpine 3.3 或更早版本”，但我在 Alpine 3.16 上遇到了上述问题，真是让人费解。

As a little bonus many popular tools also use Alpine as a base image, such nicolaka/netshoot or giantswarm/tiny-tools, with the former being specifically targeted at network troubleshooting. Good luck troubleshooting your networking when your troubleshooting tool is also broken.
作为额外福利，许多流行工具也使用 Alpine 作为基础镜像，比如 nicolaka/netshoot 或 giantswarm/tiny-tools，前者专门针对网络故障排除。当你的排查工具也坏了，祝你好运排查网络。

Beyond DNS Issues
超越 DNS 问题

While DNS is the most common issue with musl, there are more reasons to reconsider using it. Any programming language or its library that relies on C standard library is impacted by any and all differences between musl and glibc.
虽然 DNS 是 musl 最常见的问题，但还有更多理由重新考虑使用它。任何依赖 C 标准库的编程语言或其库都会受到 musl 和 glibc 之间所有差异的影响。

For Python, for example, many popular libraries such as NumPy, or Cryptography rely on C code for optimizations. Luckily, at least for some of the libraries like Numpy, chances are, you will find Alpine-based compiled package and relevant dependencies. For the less popular ones however, you might have to compile them yourself and is it really worth the hassle? In my opinion... nope. Additionally, even if you manage to build an image that includes for example numpy, its size will be ~400MB, at which point using Alpine for its small size doesn't really help much.
例如，对于 Python 来说，许多流行的库如 NumPy 或 Cryptography 都依赖 C 代码进行优化。幸运的是，至少对于像 Numpy 这样的一些库，你很可能能找到基于 Alpine 的编译包和相关依赖。不过对于不太受欢迎的，你可能得自己编译，这真的值得费心吗？我个人认为......没有。此外，即使你成功构建了一个包含 numpy 之类的镜像，它的大小也会是~400MB，这时用 Alpine 来解释它的体积小其实帮不上什么忙。

Also, the build time for such an image will be atrocious, you can try for yourself, following Dockerfile takes almost 10 minutes to build:
另外，这种镜像的构建时间会非常长，你可以自己试试，跟着 Dockerfile 构建大约需要 10 分钟：

FROM python:3.11-alpine
RUN apk --update add gcc build-base
RUN pip install --no-cache-dir numpy

Obviously, similar issues can happen also in other languages. For example Node.js uses addons, which are written in C++ and compiled with node-gyp, these will depend on C libraries and therefore on glibc.
显然，类似的问题在其他语言中也可能发生。例如，Node.js 使用插件，这些插件用 C++ 编写并用 node-gyp 编译，这些插件依赖于 C 库，因此依赖于 glibc。

Another example is Golang whose standard library - or more specifically net/http or os/user modules - depend on C libraries and therefore on glibc. Even if you don't use those particular modules, if your application requires CGO_ENABLED=1, you will obviously run into issue with Alpine.
另一个例子是 Golang，其标准库——更具体地说， 是 net/http 或 os/user 模块——依赖于 C 库，因此依赖于 glibc。即使你不使用这些特定模块，如果你的应用要求 CGO_ENABLED=1，显然你会遇到 Alpine 的问题。

What to Use Instead?
该用什么代替？

If the above issues prompted you to reconsider using Alpine, then you might be wondering what to use instead. There are plenty of options, all of them have some pros/cons/tradeoffs.
如果以上问题让你重新考虑使用 Alpine，那么你可能会想知道该用什么替代品。有很多选择，每种都有优缺点和权衡。

The biggest appeal of Alpine is its small size, so if you really care about that, then Wolfi (e.g. cgr.dev/chainguard/wolfi-base is just 12MB) or Distroless are good choices.
Alpine 最大的吸引力是它的小巧，如果你真的很在意，Wolfi（比如 cgr.dev/chainguard/wolfi-base 只有 12MB）或 Distroless 是不错的选择。

If you're looking for general purpose base image with reasonable size that's not based on musl, then you might consider using UBI (Universal Base Image) made by Red Hat, which has only 26.7MB in its "micro" version (registry.access.redhat.com/ubi8-micro) which is also fairly close to Alpine.
如果你想要一个尺寸合理且不基于 musl 的通用基础镜像，可以考虑使用 Red Hat 出的 UBI（通用基础镜像）， 它的 “微型” 版本（registry.access.redhat.com/ubi8-micro）只有 26.7MB，也相当接近 Alpine。

Another reason to choose Alpine is because of security. This also relates to its small size, because the small size generally means fewer packages and therefore also fewer vulnerabilities. The above-mentioned Wolfi images are especially good choice in this regard.
选择阿尔卑斯的另一个原因是安全性。这也与其体积小有关，因为体积小通常意味着包更少，漏洞也较少。上述 Wolfi 的照片在这方面尤其出色。

Let's be real though, chances are that saving a couple megabytes of space thanks to Alpine being small won't matter unless you're pulling the image thousands of times (which you probably shouldn't be doing anyway), so using Ubuntu or Debian-based base image wouldn't be a bad choice either.
不过说实话，Alpine 小巧节省几兆字节空间，除非你拉镜像成千上万次（其实也不该这么做），所以用 Ubuntu 或 Debian 基础镜像也不错。

Conclusion  结论

While there's nothing wrong with using Alpine and it can be great a base container image OS, I - personally - will probably never trust it again, or anything that uses musl for that matter, due to the DNS issues described earlier.
虽然使用 Alpine 没有问题，它作为基础容器镜像操作系统也不错 ，但我个人可能永远不会再信任它，或者任何使用 musl 的系统，因为之前提到的 DNS 问题。

Point of this article is not to crap on Alpine, rather it's meant to serve as warning. While Alpine might seem like a good choice - considering above listed issues - using it is at very least risky, possible reckless depending on where you plan to use it. It however ticks so many boxes and has a lot of pros, so if you're not worried about or are not impacted by the issues described in this article, you should probably keep on using it.
这篇文章的目的不是贬低阿尔卑斯山，而是作为警示。虽然考虑到上述问题，Alpine 看起来是个不错的选择，但使用它至少有风险，甚至可能因你打算在哪里使用而鲁莽。不过它满足了许多条件，优点也很多，所以如果你不担心或不受本文描述的问题影响，你应该继续使用它。

With all that said, takeaway here should be - do a reasonable amount of research before committing to using anything (whether it's container OS, framework, library) - and it being popular and well regarded doesn't necessarily mean it's automatically a good choice.
综上所述，这里的结论是——在决定使用任何东西 （无论是容器操作系统、框架还是库）之前，做合理的调研——而且它受欢迎且备受好评并不一定意味着它是个好选择。
