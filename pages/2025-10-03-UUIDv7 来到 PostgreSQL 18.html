UUIDv7 Comes to PostgreSQL 18
UUIDv7 来到 PostgreSQL 18

2025-05-09
●
8 min read
●
Gwen Shapira

PostgreSQL 18 is on the horizon, with beta testing now underway. Among the many improvements in this release is support for UUIDv7. A timestamp-based UUID variant that plays nicely with btree indexes. In this post, we'll discuss UUIDs in general, why UUIDv7 is so useful and how you'll want to use it in Postgres.
PostgreSQL 18 即将到来，目前正在进行 Beta 测试。本次发布包含了许多改进，其中包括对 UUIDv7 的支持。UUIDv7 是一种基于时间戳的 UUID 变体，与 btree 索引配合得很好。在这篇文章中，我们将讨论 UUID 的总体情况、为什么 UUIDv7 如此有用以及如何在 Postgres 中使用它。

PostgreSQL 18

PostgreSQL 18 beta 1 was released few days ago. The release is packed with new features, improvements and bug fixes. As usual, the community is encouraged to try it out and report issues, with the goal of shipping a high quality release in September.
PostgreSQL 18 Beta 1 前几天发布了。这次发布包含了许多新功能、改进和错误修复。一如既往，社区被鼓励尝试并报告问题，目标是在 9 月份发布一个高质量的版本。

The highlights of the release include:
此次发布的高亮点包括：

  • Async I/O (with io_uring) — 2-3x speedups on seq scans, vacuums
    异步 I/O（使用 io_uring）— 顺序扫描和 VACUUM 操作提升 2-3 倍速度
  • Skip scan on multi-column btree indexes + smarter OR/IN optimizations
    多列 B 树索引上的跳过扫描 + 更智能的 OR/IN 优化
  • Keep planner stats during major upgrades
    在主要升级期间保留规划器统计信息
  • UUIDv7 functions  UUIDv7 函数
  • Virtual generated columns
    虚拟生成列
  • OAuth login + md5 deprecation warning
    OAuth 登录+md5 弃用警告
  • EXPLAIN ANALYZE now shows I/O, CPU, WAL
    EXPLAIN ANALYZE 现在显示 I/O、CPU、WAL
  • Temporal constraints, LIKE on nondeterministic collation, casefolding
    时间约束、非确定性排序的 LIKE、大小写折叠
  • New wire protocol version: 3.2 (first since 2003!)
    新的网络协议版本：3.2（自 2003 年以来首次更新！）

While uuidv7() is not the most exciting feature (that would be async I/O), it's probably the most awaited one. It was close to being added in 17, and many users have been a bit disappointed that it didn't make the cut. I'm so excited about it, that I decided to take the beta for a spin and write a blog post about it.
虽然 uuidv7() 不是最令人兴奋的功能（那将是异步 I/O），但它可能是最受期待的。它在 17 版本中几乎要被加入，许多用户对它未能入选感到有些失望。我对它如此兴奋，以至于决定试用一下 beta 版本并写一篇关于它的博客文章。

What is a UUID and why are they useful?
UUID 是什么以及它们为什么有用？

UUIDs are 128-bit values used as identifiers for various items - anything from transactions to companies. They are designed to be unique across space and time and can be generated efficiently at high rates without depending on centralized services.
UUID 是 128 位的值，用作各种项目的标识符——从交易到公司。它们的设计是为了在空间和时间上保持唯一性，并且可以在高效率下生成，而不依赖于集中式服务。

Traditionally, relational databases used auto-incrementing types (like SERIAL or identity) to generate unique identifiers. This can be done efficiently on a single machine (although there are drawbacks even in this case), but once you need to scale out, you need a way to generate identifiers that are unique across all nodes. Instagram team wrote a short blog about their migration to UUIDs as they sharded their Postgres database.
传统上，关系型数据库使用自增类型（如 SERIAL 或 identity ）来生成唯一标识符。这可以在单机上高效完成（尽管在这种情况下仍有缺点），但一旦需要扩展，就需要一种能在所有节点上生成唯一标识符的方法。Instagram 团队写了一篇短博客，介绍了他们在将 Postgres 数据库分片时迁移到 UUIDs 的情况。

UUIDs are useful as primary keys in databases in several common scenarios:
UUIDs 在以下几种常见场景中作为数据库主键非常有用：

  • Generating unique IDs in a distributed database:
    在分布式数据库中生成唯一 ID：
    While many distributed databases can support auto-increment (identity) columns, they have limitations and performance issues.
    虽然许多分布式数据库可以支持自增（身份）列，但它们存在限制和性能问题。
  • Unguessable public identifiers:
    无法猜测的公共标识符：
    Properly generated, UUIDs can't be guessed, predicted or used to infer information about the system. If you use auto-increment as a customer identifier, for instance, attackers can scan all existing identifiers and attempt to use them, they can guess the next identifier and estimate how many customers you have.
    正确生成的 UUID 无法被猜测、预测或用来推断系统信息。例如，如果你使用自增作为客户标识符，攻击者可以扫描所有现有标识符并尝试使用它们，他们可以猜测下一个标识符并估计你有多少客户。
  • Allowing clients to generate identifiers:
    允许客户端生成标识符：
    Using UUIDs allows clients to generate identifiers that they can use without coordinating with the server. This is useful in mobile apps and serverless environments where you want to minimize communication to the server.
    使用 UUID 允许客户端生成他们可以在不与服务器协调的情况下使用的标识符。这在需要最小化与服务器通信的移动应用和服务器无状态环境中非常有用。

As a result of these benefits, UUIDs are used as primary keys in many databases. However, there are also 3 concerns with the use of UUIDs in databases:
由于这些优势，UUIDs 常被用作许多数据库的主键。然而，在数据库中使用 UUIDs 也存在 3 个问题：

  • Sorting: UUIDs are not meaningfully sortable by value.
    排序：UUIDs 在值上无法进行有意义的排序。
  • Index locality: New UUIDs are not close to each other in the index, this means that inserts will be performed at random locations. This can cause index bloat and other performance issues, as you can see in the charts in this blog post.
    索引局部性：新的 UUIDs 在索引中彼此不近，这意味着插入操作会在随机位置进行。正如本博客文章中的图表所示，这会导致索引膨胀和其他性能问题。
  • Size: UUIDs are 128-bit values. Most developers default to using INT (32-bit) or BIGINT (64-bit) for their primary keys. For tables with large number of very small records, this can be meaningful overhead.
    大小：UUIDs 是 128 位值。大多数开发人员默认使用 INT （32 位）或 BIGINT （64 位）作为他们的主键。对于包含大量非常小的记录的表，这会带来有意义的开销。

As I'll explain in the next section, UUIDv7 addresses 2 out of these 3 concerns.
在下一节中，我将解释 UUIDv7 解决了这 3 个问题中的 2 个。

The size of the UUID may be a problem when disk space or network bandwidth is limited, but it is worth noting that modern CPUs can compare 128-bit values in a single instruction (CMEQ, part of SIMD instructions), so database operations on UUIDs are highly optimized. The key here is to make sure you use binary representation of UUIDs (proper UUID type) in both the database and the application, and not the string representation.
当磁盘空间或网络带宽有限时，UUID 的大小可能是一个问题，但值得注意的是，现代 CPU 可以在单条指令中比较 128 位值（SIMD 指令的一部分），因此数据库对 UUID 的操作高度优化。关键在于确保在数据库和应用程序中都使用 UUID 的二进制表示（正确的 UUID 类型），而不是字符串表示。

Why UUIDv7?  为什么是 UUIDv7？

UUIDs were first standardized in RFC 4122 in 2005. This RFC defines 5 variants of UUIDs, of which variant 1 and 4 are the most common. The specification was later revised to add variants 6-8 in RFC 9562 which was published in May 2024 (although the first public working draft was published in 2020). Happy Birthday RFC 9562 and UUIDv7!
UUID 最早在 2005 年的 RFC 4122 中标准化。该 RFC 定义了 5 种 UUID 变体，其中变体 1 和 4 最为常见。该规范后来在 RFC 9562 中进行了修订，RFC 9562 于 2024 年 5 月发布（尽管第一个公开工作草案是在 2020 年发布的）。RFC 9562 和 UUIDv7 生日快乐！

To motivate the specification update, RFC 9562 discusses the common use case of using UUIDs as primary keys in databases:
为了推动规范更新，RFC 9562 讨论了在数据库中使用 UUID 作为主键的常见用例：

One area in which UUIDs have gained popularity is database keys ... but UUID versions 1-5, which were originally defined by [RFC4122], lack certain other desirable characteristics, such as:
UUID 在数据库键方面已获得流行……但最初由 [RFC4122] 定义的 UUID 版本 1-5 缺乏某些其他理想特性：

UUID versions that are not time ordered, such as UUIDv4 (described in Section 5.4), have poor database-index locality. This means that new values created in succession are not close to each other in the index; thus, they require inserts to be performed at random locations. The resulting negative performance effects on the common structures used for this (B-tree and its variants) can be dramatic.
非时间排序的 UUID 版本，如 UUIDv4（如第 5.4 节所述），数据库索引局部性差。这意味着相继创建的新值在索引中彼此不近；因此，它们需要在随机位置执行插入。这对常用结构（B 树及其变体）产生的负面影响可能非常显著。

many widely distributed database applications and large application vendors have sought to solve the problem of creating a better time-based, sortable unique identifier for use as a database key. This has led to numerous implementations over the past 10+ years solving the same problem in slightly different ways.
许多广泛分布的数据库应用程序和大型应用供应商一直寻求解决创建更好的基于时间、可排序的唯一标识符作为数据库键的问题。这导致在过去 10 多年里出现了多种实现，以略微不同的方式解决相同的问题。

The RFC proceeds to specify 16 (!) different implementations of non-standard UUIDs, each with their own trade-offs. This includes the popular ULID, Twitter's Snowflake, Instagram's ShardId and many more. All of these implementations were evaluated when designing the new specification.
RFC 继续规定了 16 个非标准 UUID 的不同实现，每个都有其自身的权衡。这包括流行的 ULID ，Twitter 的 Snowflake ，Instagram 的 ShardId 和许多其他。在制定新规范时，所有这些实现都经过了评估。

While the new RFC specifies 3 new variants of UUIDs, the only interesting one is UUIDv7. UUIDv6 is introduced for backwards compatibility only - the RFC says "Systems that do not involve legacy UUIDv1 SHOULD use UUIDv7 instead". UUIDv8 provides a format for experimental and vendor-specific extensions.
虽然新的 RFC 规定了 3 个新的 UUID 变体，但唯一有趣的是 UUIDv7。UUIDv6 仅用于向后兼容——RFC 声明“不涉及遗留 UUIDv1 的系统应使用 UUIDv7 代替”。UUIDv8 提供了一种用于实验和供应商特定扩展的格式。

UUIDv7 solves both the sorting and index locality concerns. It uses Unix Epoch timestamp as the most significant 48 bits, keeping the other 74 bits for random values (additional bits are used for version and variant). This makes UUIDs sortable by time sequence and unique. The standard also provides the option to include millisecond timestamp in the UUID and/or carefully seeded counter, to support ordering within a single second (if needed). As a result, UUIDv7 is a great fit for use as a primary key in databases - it is guaranteed to be unique, sortable and have good index locality.
UUIDv7 解决了排序和索引局部性问题。它使用 Unix 纪元时间作为最重要的 48 位，保留其他 74 位用于随机值（额外的位用于版本和变体）。这使得 UUID 可以按时间顺序排序且唯一。标准还提供了在 UUID 中包含毫秒时间戳和/或仔细种子的计数器的选项，以支持在一秒内的排序（如果需要）。因此，UUIDv7 非常适合用作数据库的主键——它保证唯一、可排序且具有良好的索引局部性。

UUIDv7 in PostgreSQL 18
PostgreSQL 18 中的 UUIDv7

Until PostgreSQL 18, UUIDv7 was not natively supported. The built-in gen_random_uuid() function generated UUIDv4, and while the popular uuid-ossp extension added support for additional UUID variants, it was limited to the variants specified in RFC 4122.
直到 PostgreSQL 18 之前，UUIDv7 都没有原生支持。内置的 gen_random_uuid() 函数生成 UUIDv4，而流行的 uuid-ossp 扩展虽然增加了对其他 UUID 变体的支持，但仅限于 RFC 4122 中指定的变体。

PostgreSQL 18 adds a new function: uuidv7(), which generates UUIDv7 values. The Postgres implementation includes a 12-bit sub-millisecond timestamp fraction immediately after the timestamp (as allowed but not required by the standard). This guarantees monotonicity for all UUIDv7 values generated by the same Postgres session (same backend process).
PostgreSQL 18 新增了一个函数： uuidv7() ，用于生成 UUIDv7 值。Postgres 的实现中，在时间戳之后立即包含一个 12 位的亚毫秒级时间戳分数（标准允许但不要求这样做）。这保证了由同一 Postgres 会话（同一后端进程）生成的所有 UUIDv7 值的严格单调性。

For consistency, PostgreSQL 18 added uuidv4() as an alias for gen_random_uuid(), to match the naming.
为了保持一致性，PostgreSQL 18 将 uuidv4() 添加为 gen_random_uuid() 的别名，以匹配命名规则。

Calling uuidv7() will generate a new UUIDv7 value where the timestamp is the current time. If you need to generate a UUIDv7 value for a different time, you can pass an optional interval to the function.
调用 uuidv7() 将生成一个 UUIDv7 值，其中时间戳为当前时间。如果你需要为不同的时间生成 UUIDv7 值，可以将一个可选的 interval 传递给该函数。

Postgres' existing functions for extracting timestamp and version from a UUID are also updated to support UUIDv7. Here is an example of how to use the new functions:
PostgreSQL 现有的用于从 UUID 中提取时间戳和版本号的函数也已更新，以支持 UUIDv7。以下是使用新函数的示例：

postgres=# select uuidv7();
                uuidv7
--------------------------------------
 0196ea4a-6f32-7fd0-a9d9-9c815a0750cd
(1 row)

postgres=# select uuidv7(INTERVAL '1 day');
                uuidv7
--------------------------------------
 0196ef74-8d09-77b0-a84b-5301262f05ad
(1 row)

postgres=# SELECT uuid_extract_version(uuidv4());
 uuid_extract_version
----------------------
                    4
(1 row)

postgres=# SELECT uuid_extract_version(uuidv7());
 uuid_extract_version
----------------------
                    7
(1 row)

postgres=# SELECT uuid_extract_timestamp(uuidv7());
   uuid_extract_timestamp
----------------------------
 2025-05-19 20:50:40.381+00
(1 row)

postgres=# SELECT uuid_extract_timestamp(uuidv7(INTERVAL '1 hour'));
   uuid_extract_timestamp
----------------------------
 2025-05-19 21:50:59.388+00
(1 row)

postgres=# SELECT uuid_extract_timestamp(uuidv7(INTERVAL '-1 day'));
   uuid_extract_timestamp
----------------------------
 2025-05-18 20:51:15.774+00
(1 row)

Using uuidv7() as the primary key in a table is straightforward, and together with the ability to extract the timestamp, it makes it easy to use the UUID as a sortable key and even inspect the creation time of the record:

CREATE TABLE test (
    id uuid DEFAULT uuidv7() PRIMARY KEY,
    name text
);

INSERT INTO test (name) VALUES ('foo');
INSERT INTO test (name) VALUES ('bar');
-- this will be sorted to the beginning of the list since we are making it 1h older than the other two
INSERT INTO test (id, name) VALUES (uuidv7(INTERVAL '-1 hour'), 'oldest');

SELECT uuid_extract_timestamp(id), name FROM test ORDER BY id;

   uuid_extract_timestamp   |  name
----------------------------+--------
 2025-05-19 19:55:43.87+00  | oldest
 2025-05-19 20:55:01.304+00 | foo
 2025-05-19 20:55:01.305+00 | bar
(3 rows)

All these functions are documented in the PostgreSQL documentation and if you are interested in the implementation details, you can review the patch.

Try it out!

Once PostgreSQL 18 is released, you will be able to use uuidv7() and all the other new functionality by installing it as you normally do. While the official release is planned for September, Beta 1 version is already available and the community encourages users to try it out and report issues.

The installations instructions for the beta versions and nightly snapshots are available here.

Final Thoughts

PostgreSQL 18 delivers practical improvements that experienced developers will really appreciate. Native support for UUIDv7 is a quiet but impactful addition that addresses long-standing pain points in database design.

UUIDs have always been a tradeoff: secure, guaranteed to be unique, efficient to generate in distributed systems. but with performance drawbacks for use with B-tree indexes. UUIDv7 brings the best of both worlds — globally unique, yet ordered in a way that plays nicely with B-tree indexes and write-heavy workloads. Postgres 18 makes them that much more convenient to use.

If you've ever hesitated to use UUIDs for primary keys, this is your chance to revisit that decision. Try the beta, test it in your schema, and see how it behaves. Whether you're building multi-tenant apps or just want more stable ID generation, UUIDv7 is worth a look.

The best way to shape the future of Postgres is to get involved early — so go ahead, spin up a test instance and let the community know what you find.
